# Synthetic Bitcoin P2P Transaction Traffic (SIH PS-5)

Generated by `generate_btc_dataset.py` (seed `20240601`, 36 simulated hours). The generator is deterministic: the same seed and GeoLite files give byte-identical output. Regenerate with:

```bash
python3 generate_btc_dataset.py --geolite-dir <folder with GeoLite2-Country CSVs> --out dataset
```

All data is synthetic. No real wallets, keys, transactions or intercepted traffic are used.

## Files

| File | Purpose |
|---|---|
| `btc_tx_traffic.csv` | The traffic, in the exact 30-column format of the official sample. **Contains no labels.** |
| `labels_transactions.csv` | Ground truth per `txid`: `label` (licit/illicit, by who spends the inputs), `typology`, `instance_id`, `step`, `spender_entities`, `involves_illicit_output` |
| `labels_addresses.csv` | Ground truth per address: owning entity, entity type, `is_illicit` (for clustering evaluation) |
| `entities.csv` | All simulated entities, including the IP of their own node if they run one |
| `seed_illicit_addresses.csv` | "Known" illicit addresses (funding addresses of ~30% of illicit actors), for graph risk propagation. Most illicit addresses are deliberately *not* listed. |
| `peers.csv` | Sensor (`dst_ip`) and peer (`src_ip`) nodes |
| `generation_metadata.json` | Full configuration, counts, excluded GeoLite blocks and verification results |

Keep label files away from model inputs; they are for training targets and evaluation only.

## What is grounded, and how it was checked

- **Geolocation:** every `src_ip` / `dst_ip` is a public IP sampled from a GeoLite2-Country block that states a country. `geo_country` is re-verified against an independent lookup of the same GeoLite files. Blocks with no country `geoname_id` (763 IPv4) or whose geoname is continent-level with no ISO code (534 IPv4) are never used.
- **Addresses:** valid Base58Check (P2PKH, P2SH) and Bech32/Bech32m (P2WPKH, P2WSH, P2TR) encodings with correct checksums, built from random hashes. The encoders pass the BIP-173 test vector.
- **Size and fees:** the `vsize` model reproduces the official sample rows exactly.
  - `fee = total_input - total_output`
  - totals are sums of the per-item satoshi amounts
  - `fee_rate = fee/vsize` (2 decimals)
- **Spending:**
  - No output is spent twice.
  - Every `input_prevouts` entry refers either to an earlier output in the file (address and amount match) or to a pre-existing output outside the dataset, like the official sample.
- **Chain timing:**
  - Blocks are ~600 s apart.
  - Each transaction confirms in a block after it was observed, never before its parents.
  - Locktime is 0 or the chain tip (anti-fee-sniping).
- **Network:**
  - Ports: peers use 8333; ephemeral ports fall in 32768–60999.
  - Geo columns describe `src_ip`, as in the official sample.
  - User agents are real Bitcoin Core releases.

The generator re-reads the finished CSV and checks all of the above, so it fails loudly instead of writing a bad file. The backend's preprocessing also reports zero invalid records.

## Modelling assumptions (synthetic, configurable in `Config`)

These are modelling choices, not real-world statistics:

- entity counts (2000 users, 50 merchants, 8 exchanges, 25 illicit actors)
- balances and payment sizes
- fee rate 1–5 sat/vB, taken from the range seen in the official sample
- about 540 normal transactions per hour
- typology parameters
- 30% of users and illicit actors broadcast through their own node

**No geography rule:** country, IP, port, user agent, fee rate, RBF and script type are generated the same way for licit and illicit entities. Only transaction-graph behaviour differs. Small residual differences come from the small illicit population and uneven activity per actor.

## Typologies

**Illicit:**

- `peeling_chain`: repeatedly peels 1–15% to exchange deposit addresses and keeps the change.
- `fan_out_split`: splits one coin into 8–25 equal outputs, then forwards each.
- `ransomware`: victims pay fresh addresses (`ransom_payment`), then the actor consolidates (`ransom_aggregation`) and peels.
- `rapid_layering`: 3–10 fast hops (1-in-1-out), cashed out at an exchange.
- `circular`: funds return to the starting address.
- `coinjoin` with an illicit participant.

**Licit look-alikes (hard negatives):**

- exchange batch payouts (fan-out)
- consolidations (fan-in)
- self-transfers and whole-coin exchange deposits (1-in-1-out)
- coinjoins among ordinary users

A mixing-like or fan-out structure is therefore **not** by itself evidence of crime.

**Note on labels:** a victim's `ransom_payment` is labelled `licit`, because the victim spends it, with `involves_illicit_output=1`.

## Known gaps

- **`asn` and `as_org` are empty.** GeoLite2-Country has no ASN data. Re-run with `--asn-csv GeoLite2-ASN-Blocks-IPv4.csv` (free from MaxMind) to fill them.
- **Scope of the data:**
  - IPv4 only by default (`--ipv6-fraction` to add IPv6).
  - One observation per transaction by default (`--extra-observation-prob` to add relay duplicates).
  - No coinbase rows.
